# デイサービス送迎ルート作成アプリ（MVP）

> 介護施設の職員が毎朝手作業で決めている送迎ルートを、
> **利用者を選ぶ → 出発時刻を入れる → ルートを作成** の3ステップで作るWebアプリ。
> Google Maps の交通状況を考慮した到着予定時刻と、A4縦の送迎表を出力します。

![status](https://img.shields.io/badge/status-MVP-blue)
![tests](https://img.shields.io/badge/tests-83%20passing-brightgreen)
![license](https://img.shields.io/badge/license-MIT-lightgrey)

**▶ すぐ試す： https://care-lab-jp.github.io/dayservice-route/**

**Google Maps の APIキーが無くても、そのまま動きます**（デモモード：推定移動時間＋簡易マップ）。
公開版もデモモードで起動するため、APIキーなしで一通りの操作を体験できます。

---

## ⚠ ご利用にあたって

- 本アプリは**実証実験段階のMVP**です。実際の送迎業務に使う場合は、必ず職員の目で内容を確認してください。
- 到着予定時刻は交通状況の予測に基づく**目安**であり、当日の状況により前後します。
- 利用者の氏名・住所は**ブラウザ内にのみ保存**され、サーバへは送信されません。
  Google へ送信されるのは座標（と住所検索時の住所文字列）のみです。
- 本ソフトウェアは無保証です（MITライセンス）。導入・運用は各施設の責任で行ってください。
- 個人情報を扱うため、共有端末での利用時は
  [GOOGLE_MAPS_SETUP.md](./GOOGLE_MAPS_SETUP.md) の「共有パソコン・タブレットで使うときの注意」を必ずお読みください。

## 1. 起動方法（ローカル開発）

```bash
cd dayservice-route
npm install
npm run dev
```

ブラウザで表示された URL（既定は http://localhost:5173 ）を開いてください。

本番ビルド：

```bash
npm run build     # dist/ に出力
npm run preview   # ビルド結果の確認
npm test          # シナリオテスト83件（vitest・実APIは呼ばない）
```

### Google Maps を使う場合（任意）

```bash
copy .env.example .env      # Windows（Mac/Linux は cp）
# .env を開いて VITE_GOOGLE_MAPS_API_KEY=... を設定
# ★ .env は起動時にしか読まれないので dev サーバを再起動すること
npm run dev
```

Google Cloud 側の設定手順は **[GOOGLE_MAPS_SETUP.md](./GOOGLE_MAPS_SETUP.md)** に
画面の順番どおりまとめてあります（初めての方はこちらから）。

有効化が必要な API は次の3つだけです。他のAPIは使用していません。

| API | エンドポイント／用途 | 未設定時の代替 |
|---|---|---|
| Maps JavaScript API | 地図表示（動的ライブラリ読込 + AdvancedMarkerElement） | SVGの簡易マップ |
| Geocoding API | 住所 → 緯度経度 | 緯度経度を手入力 |
| Routes API | `distanceMatrix/v2:computeRouteMatrix`（**出発時刻の交通状況**を考慮した移動時間・距離）<br>`directions/v2:computeRoutes`（道路に沿ったルート形状＋**渋滞区間**） | 直線距離ベースの推定 |

APIキーはコードに直接書かず `.env`（`.gitignore` 済み）で扱います。
Google 側で失敗した場合は自動で推定計算にフォールバックするため、アプリは止まりません。

### 2つの動作モード

| | APIキーなし＝デモモード | APIキーあり＝Google Maps 連携済み |
|---|---|---|
| 地図 | SVGの簡易マップ | Google地図（F＝施設、①②③＝お迎え順） |
| ルート線 | 直線 | **実際の道路に沿った線** |
| 移動時間 | 直線距離からの推定 | Routes API の実測（**出発時刻のリアルタイム交通状況**） |
| 通常時／予測／渋滞増加 | 表示なし（同値） | 3つを並べて表示 |
| 渋滞の可視化 | なし | ルート線を 順調＝緑／やや混雑＝橙／渋滞＝赤 で色分け |
| 距離 | 概算 | 実道路距離（km） |
| 住所検索 | 使用不可（座標を手入力） | 住所 → 緯度経度 |

現在の状態は**画面右上のバッジ**に常時表示されます。
（`デモモード（APIキー未設定）` ／ `Google Maps 連携済み` ／ `⚠ 接続エラー → デモモードで継続`）

## 2. 使い方（3ステップ）

1. **送迎ルート作成** タブで今日の利用者をタップして選ぶ
2. 出発時刻を入力（車両も選択可）
3. **「③ ルートを作成」** を押す

結果画面では、

- 到着予定時刻つきのルート
- 地図
- ⚠ 時間制約の警告と対策
- ドラッグ＆ドロップ／▲▼ での手動並べ替え（時刻は即再計算）
- 「印刷する」→ A4縦の送迎表

が使えます。

## 4. 交通状況を考慮したルート最適化

### 出発時刻を基準にした交通予測

送迎は「何時に出るか」で所要時間が大きく変わるため、
施設の**出発予定時刻を Routes API の `departureTime` として送信**し、
その時刻の交通状況で全区間の移動時間を計算します。

- 地点数が10以下（＝要素100以下）のときは **`TRAFFIC_AWARE_OPTIMAL`**（最も精度が高い）
- それを超える場合は **`TRAFFIC_AWARE`**（最大625要素）
- 出発時刻を既に過ぎている場合は、**翌日の同時刻**の予測に切り替えます
  （`departureTime` は未来である必要があるため）

### 順番の決定にも交通状況が効く

巡回順を決めるコスト関数の「移動時間」が、そのまま**交通考慮後の所要時間**です。

```
コスト = 交通考慮の移動時間
       + 希望時間に遅れた分 × 12
       + 早着して待つ分     × 0.6
       + 施設到着の遅れ     × 8
```

したがって、ご要望のとおり

- Aルート：通常18分 → 渋滞で31分
- Bルート：通常23分 → 現在19分

という状況では **B が選ばれます**（距離ではなく、その時刻に実際に何分かかるかで判断するため）。
距離順・直線距離順に並べる処理は一切入っていません。

### 表示

ルート結果画面に「移動時間の内訳」カードを追加しました。

```
通常時 18分 ／ 現在予測 27分 ／ 交通による増加 ＋9分（渋滞）
```

渋滞の影響が5分以上ある区間は、その利用者名とともに警告として一覧表示されます。
地図では `TRAFFIC_ON_POLYLINE` で取得した `speedReadingIntervals` を使い、
ルート線を **緑（順調）／橙（やや混雑）／赤（渋滞）** に色分けします。

## 5. ルート計算の考え方

`src/lib/routeEngine.ts` に集約しています。**最短距離だけを見ていません。**

評価コスト＝ `移動時間 + 遅れ×12 + 待ち×0.6 + 施設到着の遅れ×8`

- お迎え希望時間より早く着いた場合は「待機」として扱い、希望開始時刻まで待ちます
- 各利用者の**乗車時間補正（分）**を停車時間として加算します
- 手順：最近傍法で初期解 → 2-opt（区間反転）と or-opt（1件移動）で改善
- 利用者20名程度まで一瞬で計算できます

重みは `WEIGHTS` を書き換えるだけで現場の感覚に合わせられます。

### 「無理なルート」の警告

希望時間に間に合わない場合は、ルートを出すだけで終わらせず

- 誰に何分遅れるか
- 出発を何分早めれば間に合うか（**「間に合う出発時刻に自動調整する」ボタン**で1分刻みに逆算）
- 順番変更・別車両への分割

を提示します。待機が8分以上発生する箇所も注意表示します。

## 6. 個人情報の扱い

| データ | 置き場所 | 外部送信 |
|---|---|---|
| 氏名・備考・利用者ID | ブラウザのLocalStorageのみ | **一切しない** |
| 住所 | 同上 | 「住所から座標」ボタンを押したときのみ送信（Geocoding） |
| 緯度・経度 | 同上 | 移動時間・ルート取得のため座標のみ送信 |
| 地図上のラベル | – | `F` と `①②③` のみ（氏名なし）／内部の匿名IDは「利用者A…」 |

- 外部APIとの通信は `lib/travelProvider.ts` と `lib/googleRoutes.ts` の**2ファイルに集約**されています。ここだけ見れば送信内容を監査できます。
- `.env` は `.gitignore` 済みで、APIキーはソースコードに一切書かれていません（`.env.example` は雛形のみ）。
- `Stop.anonId`（利用者A/B/C…）を持たせてあり、将来ログや外部連携でも氏名を使わずに済みます。
- デモデータは実在の人物・住所と無関係な架空データです。

## 7. マルチテナント（複数施設のSaaS化）設計

将来、複数の施設が同じアプリを使うことを前提に、**最初から施設単位で分離**しています。

### データ分離

| 対象 | キー |
|---|---|
| テナント一覧・現在の施設 | `dayservice-route/tenants` |
| 施設ごとの業務データ | `dayservice-route/t/<tenantId>` |

- 施設を切り替えると保存先キーごと差し替えるため、**他施設のデータは読み書きできません**。
- データが無い施設へ切り替えたときは、前の施設の内容が残らないよう**必ず空状態で初期化**してから読み込みます。
- 施設を削除すると、その施設の保存データも同時に削除されます。
- サーバへ移行する際は、この `tenantId` をそのまま
  Firestore の `/tenants/{tenantId}/...` や Supabase の RLS（`tenant_id` 列）に対応させれば
  同じ分離構造を維持できます。

### 認証・課金主体の切替

「施設設定」画面で、施設ごとに次を選べます。

- **この施設のキーを使う（既定・推奨）** … その施設のGoogle Cloudプロジェクトのキー。**利用料はその施設に請求**されます
- **共通キー** … `.env` の `VITE_GOOGLE_MAPS_API_KEY`。**開発・デモ・体験利用に限定**（選択時は画面に注意表示）
- **使わない** … デモモード

キーの実体は `lib/keyVault.ts` が保持し、既定では `sessionStorage`（タブを閉じると消える）に置きます。
施設専用端末では明示的に「この端末に保存する」を選べます。

キーの解決は `lib/tenant.ts` の `resolveApiKey()` に一本化してあり、
`travelProvider` / `googleRoutes` / `MapView` はすべてこれを経由します。

## 8. 複数車両への拡張

1日分の計画は `DayPlan { tenantId, facilityId, date, routes: RoutePlan[] }` という形で保持しており、
**車両が増えれば `routes` が増えるだけ**の構造です。

- `planner.ts` の `assignMembersToVehicles()` が利用者→車両の割り当て担当です。
  現在は「有効な車両が1台なら全員そこへ」、複数なら定員を見て順に詰める単純版です。
  ここを地理クラスタリングや車いす対応車両の考慮に差し替えれば本格運用できます。
- ルート結果画面には**車両タブ**を実装済みで、`routes` が2件以上になると自動で表示されます。
- 車両ごとに `capacity` / `wheelchair` を持っているため、制約の追加も型変更なしで可能です。

## 10. エラー処理

Google側で何が起きても**アプリは落ちず、デモモードで継続**します。
発生した内容は日本語のメッセージと対処法で表示されます（`lib/apiErrors.ts`）。

| 状況 | 表示 |
|---|---|
| 人数が多く一度に計算できない | 一度に計算できる人数を超えています |
| APIキーが無効 | APIキーが正しくありません |
| APIが有効化されていない | このAPIがGoogle Cloudで有効になっていません |
| リファラー制限でブロック | APIキーの利用制限でブロックされました |
| 利用制限・上限超過 | Google Maps の利用上限に達しました |
| 住所が見つからない | 住所が見つかりませんでした |
| 道路ルートが取れない | 道路のルートを取得できませんでした |
| ネットワーク断 | ネットワークに接続できませんでした |

表示場所は3か所です。

- **ヘッダーのバッジ** … 現在のモード
- **ルート結果画面** … 地図の上に黄色の注意カード
- **施設設定画面** … 詳細＋「技術的な詳細」（開発者向けの原文）

一部の区間だけ経路が取れなかった場合は、その区間だけ推定値で補完して計算を続けます。

## 11. 既知の制限（MVPのため）

- 複数車両は「入れ物と画面」まで実装済みで、賢い自動振り分けは未実装（単純な定員詰めのみ）
- テナント分離はブラウザ内保存のため、端末をまたいだ本当のSaaSにはサーバ側の認証・RLSが必要
- 復路（お送り）ルートは未実装（データ項目のみ保持）
- デモモードの移動時間は直線距離ベースのため、実際の道路事情は反映されません
- データはブラウザごとに保存されるため、端末間で共有されません
- APIキーはブラウザから使う都合上、リファラー制限で守る方式です（完全に隠す場合はサーバ経由に変更が必要）
