# 追加レビュー：現場運用で事故りそうな穴（v0.4.0 → v0.4.1 提案）

観点：**実際のデイサービス施設で、朝の忙しい時間に職員が使ったときに何が起きるか**
方針：作り直しではなく、現在の設計を活かした最小改修

> 本書は指摘と提案のみで、コードはまだ変更していません。
> 「今すぐ直すべき」に挙げた項目は、いずれも数行〜数十行の修正で対応できます。

---

## 0. 重大度の見方

| 記号 | 意味 |
|---|---|
| **P0** | 業務が止まる／データが失われる／個人情報が漏れる。v0.4.1で直す |
| **P1** | 誤った送迎表が出る／職員が混乱する。v0.4.1〜次の版で直す |
| **P2** | 改善が望ましいが、運用でカバーできる |

## 1. APIキー設計

### 1.1 MVPとして許容できる残存リスク（ブラウザ直結方式）

| # | 残存リスク | 実際に起こること | MVPでの許容判断 |
|---|---|---|---|
| R1 | **キーは必ず端末に露出する** | DevTools・ネットワークタブ・拡張機能から読める | 許容。サーバ(BFF)無しでは原理的に不可避 |
| R2 | **Referer制限は偽装できる** | `curl -H "Referer: https://…"` で第三者が同じキーを使える | 許容（後述の防御で金額を止める） |
| R3 | **XSSがあれば sessionStorage も読まれる** | 同一オリジンのJSからは両ストレージとも読める | 許容（本アプリは外部入力をHTMLに流し込まない） |
| R4 | **拡張機能・端末管理ソフトが読める可能性** | 業務端末に入った拡張がストレージを走査 | 許容（端末管理の領域） |
| R5 | **キーの共有・使い回し** | 職員が別施設の端末に同じキーを入力 | 許容（施設ごとにプロジェクトを分ける前提で被害範囲は限定） |
| R6 | **請求は施設に届く** | 漏洩時の金銭被害は施設持ち | **要対策**：Quota上限と予算アラートを必須手順にする |

**結論：MVPとしては許容可能。** ただし R6 だけは「設定していないと事故が金額になる」ため、
セットアップ手順で任意ではなく**必須**として扱うべき（現在は「強く推奨」表記）。

### 1.2 sessionStorage / localStorage の説明に誤りがある（**P1**）

現在のドキュメント・画面文言に、次の**不正確な表現**がある。

| 現在の表現 | 正確には |
|---|---|
| 「ブラウザを閉じると消える」 | **タブ（ウィンドウ）を閉じると消える。** sessionStorage は**タブ単位**で、別タブで開き直すとキーは無く再入力が必要。なお「タブの複製」時の引き継ぎ挙動はブラウザ・複製方法によって異なるため、製品仕様として断定せず、対象ブラウザで実機確認すること |
| （暗に）sessionStorage の方が安全 | **攻撃耐性は同じ。** 同一オリジンのJSからはどちらも読める。違うのは**残る期間だけ**。「共有端末で次の人に渡らない」効果はあるが「盗まれにくい」効果はない |
| 「シークレットウィンドウを使えば残らない」 | 正しいが、**業務データも毎回消える**。利用者登録が保存されない運用になり、送迎ツールとしては使えない（1.4参照） |

**最小改修**：画面とドキュメントの文言を「タブを閉じるまで有効（別タブでは再入力が必要）」
「残る期間を短くするための設定であり、盗まれにくくする設定ではない」に修正する。

### 1.3 Referer制限・API制限・Quotaで防げる範囲

| 対策 | 防げる | **防げない** |
|---|---|---|
| HTTPリファラー制限 | 他サイトのWebページに貼られて使われること | **サーバ／curl からの直接呼び出し**（Refererは自由に詐称できる） |
| API制限 | 高額な別API（Places, Route Optimization等）への転用 | 許可した3つのAPIの濫用 |
| 割り当て(Quota)上限 | **青天井の請求**（1日の上限で頭打ち） | 上限内での濫用／上限に達した後、**自施設の業務も止まる** |
| 予算アラート | 気づくのが遅れること | 支出そのもの |

**重要な帰結**：3点セットは「漏洩を防ぐ」対策ではなく「**漏洩したときの被害額を有限にする**」対策である。
現在のドキュメントは「必ず制限をかけてください」と書いているが、
**何が防げないのか**を書いていないため、過信を招く。ここは明記すべき。

**最小改修（推奨する運用値）**

- Routes API：1日あたり `利用者数 × 4 回` 程度（例：10名なら 200/日）
- Geocoding API：1日 50 回程度（住所登録は稀）
- Maps JavaScript API：1日 200 回程度
- 予算アラート：月 1,000 円で通知

### 1.4 バックアップJSONにAPIキーは含まれるか → **含まれない（設計どおり）**

`PersistedAppData` にキーのフィールドは無く、キーは `dayservice-route/key/<tenantId>` に
別保管されているため、`exportJson()` の出力にキーは入らない。**この点は問題なし。**

ただし**回帰しやすい箇所**なので、「エクスポート結果にAPIキー文字列が含まれないこと」を
テストとして固定しておくべき（6章 T-14）。

## 2. 個人情報・バックアップ

### 2.1 JSONエクスポートで新たに生まれたリスク（**P0**）

| # | リスク | 具体的に起こること |
|---|---|---|
| E1 | **平文の個人情報ファイルが端末に残る** | 共有PCの「ダウンロード」フォルダに `送迎データ_◯◯デイサービス_2026-08-09.json` が残り、次に使う職員・清掃業者・修理業者が開ける |
| E2 | **ファイル名から施設が特定できる** | フォルダ一覧を見るだけで施設名が分かる |
| E3 | **メール・USBで気軽に持ち出せる** | 「家で作業する」ために添付・コピーされる。事業所の持ち出し規程に抵触しうる |
| E4 | **削除したつもりが残る** | ゴミ箱・クラウド同期フォルダ（OneDrive/Googleドライブ）に残存 |

**皮肉なことに、エクスポート機能は「LocalStorageに個人情報が残る問題」を解決するために追加したが、
より持ち出しやすい形（ファイル）を作ってしまっている。**

**最小改修**

1. エクスポート時に**確認ダイアログ**を出す
   「利用者◯名の氏名・住所を含むファイルを保存します。保存先と取り扱いにご注意ください。」
2. ファイル名から施設名を外す（例：`soso-backup-2026-08-09.json`）
3. JSON先頭に警告を入れる（`"_warning": "このファイルには利用者の個人情報が含まれます"`)
4. 画面に「保存後はUSB・メール添付での持ち出しを避け、不要になったら削除してください」を常時表示

### 2.2 JSONに含めるべきもの／含めてはいけないもの

| 含める | 理由 |
|---|---|
| 施設情報・利用者・車両・出発時刻の設定 | 復元に必須 |
| スキーマバージョン・書き出し日時・アプリ名 | 検証に必要 |

| **含めない** | 理由 |
|---|---|
| APIキー（現状も未含有） | 秘密情報。ファイルとして持ち出されると被害が拡大 |
| `dayPlan`（作成済みルート） | **その日限りの一時データ**。ポリラインで肥大化し、復元価値も低い。現状は含まれており不要 |
| `history`（過去ルート） | 業務再開に不要。**「誰がいつ送迎されたか」という行動履歴**であり、持ち出す情報を最小化すべき。オプション扱いが妥当 |
| 備考欄 | 「認知症」「独居」等の要配慮情報が入りうる。**含める／含めないを選べる**のが望ましい |

**最小改修**：エクスポート時に「利用者情報のみ（推奨）／全データ」を選べるようにし、
既定を前者にする。`dayPlan` は既定で除外する。

### 2.3 インポートの検証が甘い（**P0**）

現在の `importJson()` は `members` が配列で `facility` があれば通してしまう。

| 欠けている検証 | 起こる事故 |
|---|---|
| **schemaVersion の確認** | 将来の新形式・過去の旧形式をそのまま流し込み、画面が壊れる／黙って項目が欠落する |
| **tenantId の照合** | **A施設のバックアップをB施設に取り込んで、他施設の利用者情報が混ざる**（分離設計が崩れる最悪ケース） |
| **件数・型の妥当性** | 座標が文字列、時刻が `"25:99"`、`boardingMinutes` が負数でも通る |
| **上書き前の退避** | 取り込みで既存データが即消える。取り消せない |
| 改ざん検知 | 署名等は無い（MVPでは過剰なので不要） |

**最小改修**

```
importJson():
  1. app名 と schemaVersion を検証（未知バージョンは拒否、旧版はmigrateを通す）
  2. tenantId が異なる場合は「別の施設（◯◯）のデータです。取り込みますか？」と明示確認
  3. members/facility の必須項目と型を最低限チェック（座標が数値、時刻がHH:MM）
  4. 取り込み前に現在のデータを自動退避（dayservice-route/t/<id>/backup）
  5. 取り込み結果を「利用者◯名・車両◯台を読み込みました」と件数で表示
```

改ざんそのものは、ローカル完結のMVPでは**防御対象にしない**のが妥当。
（同じ端末の利用者はLocalStorageも直接書き換えられるため、JSONだけ守っても意味がない）

### 2.4 「シークレットウィンドウ推奨」は現場向きではない（**P1・自己訂正**）

シークレットウィンドウでは**閉じた時点で利用者登録も施設設定も消える**。
毎朝ゼロから利用者を登録し直すことになり、送迎ツールとして成立しない。
さらに一部ブラウザでは `localStorage` の書き込みが制限され、
**エラーも出ないまま保存されない**（2.5参照）状態になる。

**訂正後の推奨**

| 端末の性質 | 推奨 |
|---|---|
| 施設の業務端末（共有だが施設内） | **通常ウィンドウ＋端末のPIN/パスワードロック＋職員別OSユーザー**。使用後の削除は不要 |
| 一時的に借りた端末・私物 | シークレットウィンドウ、または使用後に「この端末のデータを削除」 |

### 2.5 保存の失敗が黙って握りつぶされる（**P0**）

`lib/storage.ts` は `setItem` の例外を `catch { /* ignore */ }` している。
容量超過（LocalStorageは一般に数MB程度の容量制限があり、**ブラウザ・環境によって異なる**）、
Safariのプライベートモード、ブラウザのストレージ制限などで
**保存に失敗しても職員には何も表示されない**。

朝に利用者を10名登録 → 実は1件も保存されていない → 翌日すべて消えている、という事故が起こりうる。

**最小改修**

```
setItem 失敗時：
  1. コンソールだけでなくアプリ状態に「保存に失敗しました」を記録
  2. 画面上部に赤帯で常時表示（消えない）
  3. 「データを書き出す」を促す（メモリ上のデータはまだ生きているため救出できる）
```

容量超過の主因になりやすいのは `dayPlan.encodedPolyline` の保持なので、
**保存前にポリラインを落とす**（再取得可能なため）だけでも実効性がある。

## 3. ルート最適化

### 3.1 係数に根拠がないことの問題（**P1**）

現在の重み（遅れ×12／遅れ人数×30／待機×0.6／施設遅延×8／車内超過×3）は
**私が設計時に置いた仮の値であり、実測にも現場ヒアリングにも基づいていない。**
これ自体はMVPとして許容範囲だが、次の問題がある。

| 問題 | 具体例 |
|---|---|
| **施設ごとの価値観の違いを表現できない** | 「多少遅れても一人ずつ丁寧に」の施設と「定刻厳守」の施設で最適解は違う |
| **説明できない** | 職員に「なぜこの順番？」と聞かれたとき、根拠が「係数がそうだから」になる |
| **暗黙のトレードオフ** | 遅れ12 : 待機0.6 = 20倍。つまり「20分待つ方が1分遅れるよりマシ」と宣言している。これが施設の意図と一致している保証はない |
| **単位の混在** | 「分」と「人」を1つの式で足しており、`lateFixedPenalty=30` は「遅れる人が1人増える ≒ 移動が30分延びる」と等価。これは強い主張 |

**最小改修（設計は変えない）**

1. `WEIGHTS` を**テナント設定に載せる**（既定値は現行のまま）。
   施設設定に「時間厳守寄り ⇔ ゆったり寄り」の**3段階プリセット**だけ用意し、
   数値そのものは上級者向けに隠す。
2. 画面の警告文に「この施設の設定（時間厳守寄り）で判断しています」と表示し、説明可能にする。
3. `evaluateOrder()` は既にあるので、係数変更の影響をテストで固定できる。

### 3.2 車内滞在は「最大」だけでなく「分布」を見るべきか（**P1**）

現在は `rideMin > maxRideMinutes` の**超過分の合計**をコストにしている。これは
「1人が30分超過」と「3人が10分ずつ超過」を同一視する点で、1.の遅れと同じ問題を抱えている。

現場的に意味があるのは次の3つ。

| 指標 | 現場での意味 | 現状 |
|---|---|---|
| 最大車内時間 | 一番かわいそうな人がどれだけ乗っているか | 個別に警告あり |
| **超過人数** | 「今日は3人が長時間になる」 | **未表示** |
| 平均車内時間 | 便全体の負担感 | **未算出** |

**最小改修**：`RoutePlan` に `maxRideMin` / `avgRideMin` / `rideOverCount` を持たせ、
結果画面の「移動時間の内訳」に1行足す（「車内時間 平均24分／最長42分／目安超過1名」）。
コスト関数には**超過人数の固定ペナルティ**を足す（遅れと同じ考え方で一貫させる）。

### 3.3 多点スタート＋2-opt＋or-opt で十分か → **十分**

| 規模 | 判断 |
|---|---|
| 〜20名／1台 | **十分。** 実測で数十ms、局所最適も多点スタートで実用上回避できている |
| 20名超／複数台 | 割当と順序の同時最適化が必要になり、現在の構成では不足。ただしMVPの範囲外 |

**より効くのはアルゴリズムより入力の質**である。座標の精度（3.4）と移動時間の精度の方が、
探索手法の差より結果に効く。ここに労力を割くべきではない。

### 3.4 併せて気づいた点（**P1**）

- **同一住所の2名**（夫婦・同施設入居）で、区間移動時間が最低1分に丸められている
  （`Math.max(1, …)`）。5組いれば5分の架空の移動時間が積まれる。
  **最小改修**：同一座標間は0分にする（乗車時間補正は別途加算されるので問題ない）。
- **同点の順番**が複数あるとき、どれが選ばれるかは配列順で決まる。
  職員には「日によって順番が変わる」と映る。
  **最小改修**：同点なら**前回ルートと同じ順番を優先**する（履歴を既に持っているので実装可能）。
  これは現場の納得感に直結する。

## 4. おすすめ出発時刻

### 4.1 「おすすめ」と「最遅出発可能」は分離すべき（**P1**）

**現在、実は2つの異なる推奨が同時に画面に出ている。**

| 表示 | 実体 | 意味 |
|---|---|---|
| 最上部パネルの「おすすめ出発時刻」 | `recommendBestDepart()` | 間に合う中で**コスト最小**（待機も少ない）時刻 |
| 警告カードの「出発時刻を◯分早める」／「間に合う出発時刻に自動調整する」 | `suggestDepartMin()` | 間に合う中で**最も遅い**時刻（＝最遅出発可能時刻） |

この2つは**別の時刻を指すことがある**（例：おすすめ 07:50／最遅 07:58）。
職員から見れば「アプリが2つ違うことを言っている」状態で、混乱の元。

**最小改修（表示を変えるだけ、ロジックは既存のまま）**

```
┌ 今日の出発時刻 ──────────────────────────┐
│  現在の設定 08:00                                    │
│  おすすめ   07:50   （余裕をもって回れる）  [これにする] │
│  最遅       07:58   （これより遅いと間に合わない）      │
└──────────────────────────────────────┘
```

「最遅」を明示すると、朝の遅れが出たときに職員が自分で判断できる。
現場的価値は「おすすめ」より高い可能性がある。

### 4.2 −90〜+30分／1分刻みの境界ケース（**P1**）

| # | ケース | 現在の挙動 | 提案 |
|---|---|---|---|
| B1 | 最適が探索範囲の**端**（−90分）にある | 端の値をそのまま「おすすめ」として返す。実際はもっと早い方が良い可能性 | 端に張り付いたときは「90分以上早める必要があります」と表示し、断定しない |
| B2 | 出発時刻が **01:30 より前** | `departMin − 90` が負になり、`toHHMM()` の剰余で **前日22:30 などに見える** | 0分未満は 00:00 でクランプ |
| B3 | +30分側が足りない | 全員の希望が10:00開始なのに8:00出発だと、待機を減らす最適解が範囲外 | +30 → +60 に広げる（計算量は151回のシミュレーションで無視できる） |
| B4 | 実行可能解が**複数**あり同コスト | 先に見つかった（＝より早い）方が選ばれる | 同コストなら**遅い方**を選ぶ（無駄に早く出ない）方が現場的 |
| B5 | 利用者0名 | `departMin` をそのまま返す | 問題なし |
| B6 | 深夜・日跨ぎ | 送迎業務では発生しないため考慮不要 | 許容 |

### 4.3 「おすすめ」が現場感覚と逆転する可能性（**P1**）

**逆転しうる。** 具体例：

| 状況 | アプリの判断 | 現場の感覚 |
|---|---|---|
| 全員の希望が8:30〜、現在8:00出発 | 待機が減るので「**30分遅らせても間に合います**」 | 「早めに出て玄関前で待つ方が安心。遅れたときの余裕がない方が怖い」 |
| 渋滞が読めない日 | 予測に合わせてギリギリの時刻を提案 | 「予測は外れる。5分は余裕を持ちたい」 |

原因は、コスト関数が**待機を悪**（0.6/分）とだけ扱い、
**余裕（バッファ）を善**として評価していないこと。

**最小改修**

1. **安全マージン設定**（施設ごと、既定5分）を導入し、おすすめ時刻から一律で引く。
2. 「遅らせても間に合います」は**提案せず情報提供に留める**
   （ボタンは出さず「◯分遅らせても間に合う計算です」と表示するだけ）。
   早める方向は事故防止なのでボタンを出す、という非対称にする。

## 5. 車両割当

### 5.1 「定員＋車いす対応」の単純割当をMVPで残す妥当性 → **妥当**

- MVPの想定は1台1便であり、複数台は「将来」。現状の割当は**入れ物としての正しさ**を担保する役割で十分。
- ただし現在の実装には次の穴がある（**P1**）。

| # | 穴 | 起こること |
|---|---|---|

### 8.2 MVPでは許容してよい

| # | 内容 | 理由 |
|---|---|---|
| 1 | ブラウザからの直接API呼び出し（キー露出 R1〜R5） | サーバ無しでは原理的に不可避。Quota上限で金額被害を有限化できる |
| 2 | Refererが詐称可能であること | 上と同じ。防御はQuotaと予算アラート |
| 3 | 係数に実測根拠が無いこと | 現場で使いながら調整するのがMVPの正しい進め方。ただしプリセット化は早めに |
| 4 | 複数車両の割当が単純（地理を見ない） | MVPは1台1便。V2は将来課題 |
| 5 | 2タブ同時編集の競合 | 単一端末・単一職員の運用が前提。後勝ちで許容 |
| 6 | JSONの改ざん検知が無い | 同じ端末ならLocalStorageも直接書き換え可能で、JSONだけ守っても無意味 |
| 7 | 復路（お送り）未実装 | 往路の価値が先。データ項目は保持済み |
| 8 | 履歴が30件で打ち切り | 分析用途はSaaS化以降 |
| 9 | 利用者24名超で分割が必要 | 1台の定員を超えており、実運用でも便を分ける |

### 8.3 SaaS化するときに必ず直す

| # | 内容 | 理由 |
|---|---|---|
| 1 | **APIキーをサーバ保管に**（BFF経由、ブラウザには短命トークン） | 施設をまたぐと鍵管理・ローテーションが端末運用では破綻する |
| 2 | **認証とロール**（施設管理者／職員／運転手） | 誰でも全利用者を削除できる状態は監査に耐えない |
| 3 | **サーバ側のテナント分離**（Firestore パス／Supabase RLS） | クライアント側の保存キー分離は「同じ端末で混ざらない」以上の保証がない |
| 4 | **監査ログ**（誰がいつ閲覧・変更・エクスポートしたか） | 介護事業者の内部統制・個人情報の取扱記録 |
| 5 | **エクスポートの権限制御と記録** | 現状は誰でも全個人情報を持ち出せる |
| 6 | **バックアップと保持期間・削除要求への対応** | 法令対応 |
| 7 | **同時編集の競合解決**（楽観ロック等） | 複数職員の同時利用が前提になる |
| 8 | **係数の施設別設定をサーバ管理に** | 端末ごとに違う設定で計算される状態を避ける |
| 9 | **複数車両・複数便の本格最適化** | 施設規模が大きくなると必須 |
| 10 | **利用量・課金の可視化** | 施設ごとのAPI利用量を運営・施設双方が把握できる必要がある |

## 9. 補足：今回のレビューでの自己訂正

前回（v0.4.0）のレビューで私が書いた次の2点は、今回の検証で**不適切**と判断した。

1. 「共有端末ではシークレットウィンドウを使う」
   → 業務データも消えるため送迎ツールとして成立しない。端末ロック＋OSユーザー分離を主にすべき（2.4）。
2. 「エクスポート機能で個人情報の残存問題に対処した」
   → **ファイルという、より持ち出しやすい形**を作った側面がある。警告と既定の絞り込みが必要（2.1）。
