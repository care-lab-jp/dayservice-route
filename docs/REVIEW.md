方針：既存のUI・アルゴリズムを壊さず、MVPとして現実的な範囲で改善する

## 1. Google Maps APIキー設計

### 1.1 レビュー（改修前の問題）

| 問題 | 内容 | 深刻度 |
|---|---|---|
| 既定が逆 | 新規施設の既定が「運営者の共通キー」だった。運営者の請求書に全施設の利用が乗る | 高 |
| 責務の混在 | `Tenant.mapsApiKey` にキー本体を持たせ、テナント設定とシークレットが同じJSONに同居 | 中 |
| 保存が無条件permanent | 共有PCでも `localStorage` に平文で永続保存。次の利用者がDevToolsで参照できる | 高 |
| Map IDの誤用 | `DEMO_MAP_ID` を固定。**Googleはテスト専用と明記**しており本番利用は不可 | 中 |
| 課金SKUの認識 | `TRAFFIC_AWARE(_OPTIMAL)` は **Compute Routes Pro** 課金。無料枠が Essentials より少ないことが未考慮 | 中 |

### 1.2 改修内容

**責務を3つに分離した。**

| 責務 | 置き場所 | 内容 |
|---|---|---|
| 誰の契約で使うか | `Tenant.keyMode` | `own`（施設自身＝既定）／`shared`（開発・デモ）／`none`（デモモード） |
| キーをどこに置くか | `Tenant.keyStorage` | `session`（既定・タブを閉じると消える）／`local`（施設専用端末のみ） |
| キーの実体 | `lib/keyVault.ts` | テナント設定JSONから分離。`dayservice-route/key/<tenantId>` |

- **新規施設の既定は `own`。** 「共通キー」ボタンは環境変数が設定されている場合のみ有効で、選ぶと画面に
  「⚠ 共通キーは開発・体験用です」と常時表示される。
- **Map ID を施設ごとに設定可能**にした（未設定時のみ `DEMO_MAP_ID`、画面に注意書き）。
- **交通状況のON/OFFを施設ごとに選べる**ようにした。OFFなら `TRAFFIC_UNAWARE` を使い
  Essentials SKU（無料枠が多い）で計算する。費用を自分で持つ施設にとって重要な選択肢。
- 旧 `useOwnKey` / `mapsApiKey` は起動時に自動移行する（`migrateTenant()`）。

### 1.3 LocalStorage にAPIキーを置くことの評価

**前提：ブラウザから直接Google APIを呼ぶ限り、キーは必ず端末に露出する。**
`localStorage` を `sessionStorage` に変えても、難読化しても、DevToolsやネットワークタブから見える。
つまり「隠す」対策は本質的に効果がない。実効性のある防御は次の3つで、いずれもGoogle Cloud側の設定である。

1. **HTTPリファラー制限** … そのURL以外では使えない（キーが漏れても他所で使えない）
2. **API制限** … Maps JavaScript / Geocoding / Routes の3つのみ
3. **割り当て（Quota）の上限** … 1日あたりの上限を決め、暴走請求を物理的に止める

その上で本アプリが取った現実的なMVP改善は次のとおり。

| 対策 | 効果 |
|---|---|
| 既定を `sessionStorage` に | 共有PCで**ブラウザを閉じればキーが残らない**。次の職員・次の利用者に渡らない |
| 永続保存は明示的な選択に | 「この端末に保存する（施設専用端末向け）」を選んだときだけ `localStorage` |
| 画面にマスク表示 | `AIzaSy********abcd` と保存場所を表示し、意図しない永続化に気づける |
| 「キーを削除」ボタン | 退職・端末返却時にすぐ消せる |
| 施設削除時に自動削除 | テナント削除でキーも消える |

**将来のサーバ経由（BFF）への移行余地は維持している。** 呼び出し側は `getApiKey()` しか見ておらず、
これを「サーバが発行した短命トークンを取得する」実装に差し替えれば、
`travelProvider` / `googleRoutes` / `MapView` は無変更で済む。

## 2. 個人情報・データ保存

### 2.1 レビュー

| 観点 | 現状 | 評価 |
|---|---|---|
| Googleへの送信 | 氏名・備考は送らず、座標のみ。地図ラベルは `F`／`①②③` | **良好。維持** |
| 保存場所 | 利用者名・住所・備考が `localStorage` に平文 | 共有端末では残り続けるのが問題 |
| 端末間の混在 | テナント別キーで分離済み | 良好 |
| バックアップ | 手段なし。ブラウザのデータ削除で全消失 | **要改善** |
| 退出時の後始末 | 手段なし | **要改善** |

デイサービスの現実として、事務所のPCやタブレットは**複数職員の共用**であり、
家族対応中に画面を見られることもある。ブラウザに氏名・住所が残り続ける設計は避けたい。

### 2.2 改修内容（現段階で実装すべき最低限）

1. **データの書き出し（バックアップJSON）** — 端末故障・ブラウザ初期化への備え
2. **データの取り込み** — 端末入れ替え・別端末への移行
3. **「この端末のデータを削除」** — 共用端末の利用後に実行できる
4. **運用手順の明記**（施設設定画面に常時表示）
   - 端末にPIN／パスワードロックをかけ、離席時はロックする
   - 職員ごとにOSユーザーを分ける（ブラウザ保存領域も分かれる）
   - 共用端末ではシークレットウィンドウを使う（閉じれば残らない）

**あえて実装しなかったもの**とその理由：

| 案 | 判断 |
|---|---|
| アプリ独自のPINロック | ブラウザ内のデータは暗号化されないため、PINは「見た目の鍵」にしかならない。OS／端末ロックの方が確実。サーバ認証と同時に導入すべき |
| LocalStorageの暗号化 | 鍵も同じ端末に置くことになり、実効性がない。誤った安心感を与えるため不採用 |

### 2.3 サーバ移行時（Firebase / Supabase）の設計

| 層 | 移行後 |
|---|---|
| 保存 | `TenantRepository` の実装を差し替えるだけ（`load` / `save` / `clear` / `exportJson` / `importJson`） |
| 分離 | Firestore `/tenants/{tenantId}/…`、Supabase は `tenant_id` 列 + RLS |
| 個人情報 | 氏名・住所はサーバ側で保管し、**Google APIへ送るのは座標のみ**という原則は不変 |
| 監査 | 外部送信は `travelProvider.ts` / `googleRoutes.ts` の2ファイルに集約したまま |

## 3. 送迎ルート最適化のレビュー

### 3.1 「最近傍法 → 2-opt → or-opt」は妥当か

**結論：構成自体は妥当。** 利用者10〜20名という規模では厳密解を求める必要がなく、
毎朝ブラウザで即座に返る応答性の方が価値が高い。
また評価関数が「距離」ではなく「交通考慮の所要時間＋希望時間違反」なので、
デイサービスの要件（時間を守る）に沿っている。

ただし、現場観点で**3つの欠落**があった。

| # | 問題 | 現場での意味 | 対応 |
|---|---|---|---|
| A | 初期解が1つだけ | 希望時間の並び次第で明らかに悪い順番に落ち込む（局所最適） | **多点スタート**を実装 |
| B | 遅れが線形評価 | 「1人が20分遅れ」と「4人が5分ずつ遅れ」が同点。現場は前者を選びたい | **遅れ1人につき固定ペナルティ30**を追加 |
| C | 車内滞在時間が無評価 | 最初に乗った方が50分以上乗りっぱなしでも警告が出ない。高齢者にとっては重大 | **`maxRideMinutes`（既定40分）と警告・ペナルティ**を追加 |

### 3.2 改修後のコスト関数

```
コスト = Σ 交通考慮の移動時間
       + Σ 希望時間の遅れ × 12
       + （遅れた人数） × 30            ← 追加
       + Σ 早着の待機 × 0.6
       + 施設到着の遅れ × 8
       + Σ 車内滞在の超過分 × 3          ← 追加
```

- 多点スタート：利用者12名以下は全員を先頭候補に、13名以上は「締切が早い4名」を候補にして
  それぞれ 2-opt / or-opt を回し、最良を採用する。
- 車内滞在時間は施設到着時刻が決まって初めて確定するため、シミュレーション後に一括計算する。

### 3.3 検証

- 「通常時は近いが渋滞している家」より「遠いが順調な家」を先に回ることをテストで確認（`04` 群）
- 総遅延が同じ12分でも、**遅れる人数が少ない案**を選ぶことをコスト比較で確認（`03` 群）
- 15名で計算時間 1秒未満（実測 数十ms）
- 多点スタートの結果が素朴な順序より悪くならないことを確認

### 3.4 残す判断（変更しないもの）

- 厳密解（分枝限定など）は導入しない。20名規模では体感差がなく、保守コストだけ増える
- Google の Route Optimization API は使わない。別課金・別体系で、MVPの費用前提に合わない

## 5. UI/UX：「結局、今日は何時に出ればいいのか」

### 5.1 レビュー

改修前は、出発時刻の情報が「操作バーの中の小さな数字」と「警告文の対策リストの1行目」に散っていた。
朝の忙しい時間に**最初に見るべき情報が最初に無い**状態だった。

### 5.2 改修内容

ルート結果画面の**最上部**に、次の1枚を追加した（他のカードは従来のまま）。

```
┌ 今日は何時に出発すればよいか ───────────────────────┐
│  現在の設定      おすすめ出発時刻      5分 早めてください      │
│    08:00            07:55            [おすすめに合わせる]     │
│                                                              │
│  ⚠ 希望時間に間に合わない方 1名 ／ 渋滞による増加 ＋9分       │
│  施設到着予定 09:10（希望 09:15）                             │
└──────────────────────────────────────────────┘
```

- **おすすめ出発時刻**は `recommendBestDepart()` が −90分〜+30分を1分刻みで探索し、
  「全員が希望時間に間に合い、施設到着にも間に合う案のうちコスト最小（＝無駄な待機も少ない）」を返す。
- 4状態を色で区別：`ok`（緑）／`earlier`・`later`（琥珀）／`impossible`（赤）。
- 「おすすめに合わせる」1クリックで出発時刻を変更し、時刻を再計算する。
- ダッシュボードの「出発予定」カードにも、おすすめ時刻を併記した。

これにより、**画面を開いた瞬間に「何時に出るか」「何分早めるか」「誰が危ないか」**が分かる。

## 6. 過去ルート

### 6.1 実装内容

- ルート作成時に履歴を1件積む（新しい順・最大30件、`RouteHistoryEntry`）。
  ポリラインなど重いデータは保存せず、**巡回順・出発時刻・移動時間・施設到着・エラー有無**のみ。
- **作成画面**：同じ顔ぶれの前回ルートがあればカードで提示し、
  「前回と同じ順番で作る」ボタンで前回順のまま時刻だけ再計算できる。
- **結果画面**：前回との比較カードを表示（順番が同じか／移動時間の増減／施設到着の差）。
  「前回と同じ順番に戻す」も可能。

毎日同じ顔ぶれの施設では、**職員が慣れた順番を維持しつつ、その日の交通状況だけ反映**できる。
これは「毎日アルゴリズムが違う順番を出してくる」ことへの現場の抵抗を避ける意味でも重要。

### 6.2 将来

`RouteHistoryEntry` に実績（実際の到着時刻）を足せば、
「いつも時間がかかる場所」の分析や移動時間の学習補正につなげられる。

## 7. SaaS化：責務の整理

| 対象 | 現在の置き場所 | サーバ化後の置き場所 | 移行時の作業 |
|---|---|---|---|
| 認証 | なし（端末＝境界） | Firebase Auth / Supabase Auth | 新規。ログイン画面とセッション管理 |
| Tenant | `dayservice-route/tenants`（`lib/tenant.ts`） | `tenants` コレクション／テーブル | ユーザーとテナントの所属関係を追加 |
| Facility / Member / Vehicle / DayPlan / History | テナント配下の1集約（`PersistedAppData`） | `/tenants/{id}/…` または `tenant_id` 列 + RLS | `TenantRepository` の実装差し替えのみ |
| Google API利用設定 | `Tenant.keyMode` ほか＋`keyVault` | サーバ保管。ブラウザへは短命トークンのみ | `getApiKey()` の実装差し替え |
| ルート計算 | ブラウザ（`routeEngine`） | そのまま or サーバ移設のどちらも可 | 純粋関数のため移設容易 |

**改善として `lib/repository.ts` を新設**した。集約の単位を「テナント1件ぶんの業務データ」としたのは、
送迎業務が常に1施設ぶんをまとめて読み書きするためで、
Firestore の1ドキュメント／Supabase の1行にも自然に対応する。

## 8. 仕様書・実装の記載誤り（訂正済み）

| # | 誤り | 正 | 影響 |
|---|---|---|---|
| 1 | 「毎月の無料枠（＄200クレジット）」という前提 | **2025年3月以降、$200クレジットは廃止**され、SKUごとの無料枠（Essentials 10,000／Pro 5,000／Enterprise 1,000 呼び出し/月）に変更 | 費用見積りの前提が変わる。ドキュメントを訂正 |
| 2 | `TRAFFIC_AWARE(_OPTIMAL)` の課金区分を明記していなかった | 交通考慮は **Compute Routes Pro** SKU（無料枠5,000/月）。交通なしは Essentials | 交通OFF設定を実装し、選択できるようにした |
| 3 | `mapId: 'DEMO_MAP_ID'` を固定 | **DEMO_MAP_ID はテスト専用**。本番では自前のMap IDが必要 | 施設ごとにMap IDを設定可能にした |
| 4 | 「利用者24名超は計算不可」 | 正しいが、`TRAFFIC_AWARE_OPTIMAL` は**利用者8名（10地点）まで**という制約の方が先に効く | 表現を明確化 |

**誤りではなかった（確認済み）項目**：
`computeRouteMatrix` の要素上限（TRAFFIC_AWARE_OPTIMAL=100／その他=625）、
エンドポイントURL、`departureTime` は未来時刻必須、
`extraComputations: TRAFFIC_ON_POLYLINE` と `speedReadingIntervals` の組み合わせ、
`google.maps.Marker` が非推奨で `AdvancedMarkerElement` が現行、の各点。

## 10. 既存機能への影響

| 項目 | 影響 |
|---|---|
| 画面デザイン | **変更なし**（色・カード・ボタン・ナビはそのまま）。追加したのはカード2枚と入力欄3つ |
| 既存データ | `version: 3` の移行処理で自動変換。**利用者・施設情報は失われない**。作成済みルートのみ破棄（作り直しが容易なため） |
| 旧APIキー設定 | `useOwnKey: true` だった施設は `keyMode: 'own'` + `keyStorage: 'local'` へ自動移行し、キーも引き継ぐ |
| デモモード | 変更なし。APIキーなしで全機能が動作 |
| 巡回順 | 多点スタートと新ペナルティにより、**従来と異なる順番になる場合がある**（より良い方向へ）。既存の並べ替え操作は従来どおり |
| 費用 | 交通ONのまま使えば従来と同じ。OFFを選べば安価になる |
| ビルド | 追加依存は `vitest`（開発時のみ）。本番バンドルは 226→240KB（gzip 79KB） |

## 11. 今後サーバー化するときに残る課題

1. **認証と権限** — 施設管理者／一般職員／運転手のロール設計。現状は端末を持つ人＝全権
2. **APIキーのサーバ保管** — BFFを立て、ブラウザには短命トークンのみ渡す。`getApiKey()` の差し替えで対応可能だが、キー管理・ローテーションの運用設計が必要
3. **同時編集** — 複数職員が同時に利用者を編集した場合の競合。現状は最後の保存が勝つ
4. **監査ログ** — 誰がいつ利用者情報を閲覧・変更したか。介護事業者の内部統制で求められることがある
5. **バックアップと保持期間** — 送迎記録の保存年限、削除要求（本人・家族）への対応
6. **オフライン運用** — 現地でネットワークが切れた場合の同期方針（現状はローカル完結なので実は強い）
7. **課金の把握** — 施設ごとの利用量を運営が把握する仕組み（現状は各施設のGoogle Cloudコンソールでのみ確認可能）
8. **複数車両の本格対応** — 現在は定員・車いすを見た単純割当。エリア分割や乗車時間の均等化は未実装
9. **復路（お送り）** — データ項目は保持済みだが計算は未実装
10. **法令・規程対応** — 個人情報保護法上の安全管理措置、委託先（Google）の取り扱い明示、施設の運営規程との整合
